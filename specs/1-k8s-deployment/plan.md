# Implementation Plan: Cloud-Native Kubernetes Deployment

**Branch**: `1-k8s-deployment` | **Date**: 2026-01-07 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/1-k8s-deployment/spec.md`

## Summary

Deploy the Phase III Todo AI Chatbot to a local Kubernetes cluster using Minikube, leveraging the Agentic Dev Stack (Gordon, kubectl-ai, kagent, Claude) for infrastructure-as-code generation. The system comprises three independently containerized microservices (Frontend, Backend, Database) deployed via Helm charts with cloud-native best practices (health probes, resource limits, secrets management, rolling updates).

**Technical Approach**: Multi-stage Docker builds with Alpine base images minimize attack surface and image size. Helm charts provide templated, versioned deployments with values.yaml configuration. Kubernetes Services enable internal DNS-based communication (backend-service:5000, mongodb-service:27017). Frontend exposed via NodePort or Ingress for browser access. Automated validation ensures deployment succeeds in under 10 minutes with comprehensive smoke tests.

## Technical Context

**Language/Version**:
- **Frontend**: JavaScript/TypeScript (React application, built with Node.js 18)
- **Backend**: JavaScript/TypeScript (Node.js 18 LTS)
- **Infrastructure**: YAML (Kubernetes manifests, Helm templates)
- **Shell**: Bash (validation scripts)

**Primary Dependencies**:
- **Container Runtime**: Docker 20.10+ (with Docker AI Agent Gordon if available)
- **Orchestration**: Kubernetes 1.28+ (via Minikube 1.32+)
- **Package Manager**: Helm 3.12+
- **Base Images**: Alpine Linux 3.18+, Nginx 1.25-alpine, Node.js 18-alpine, MongoDB 7
- **AI Agents**: Gordon (Dockerfile generation), kubectl-ai (deployment assistance), kagent (cluster analysis)

**Storage**:
- **Database Persistence**: MongoDB with PersistentVolumeClaim (5Gi) on Minikube's "standard" StorageClass (hostPath-based local storage)
- **Image Storage**: Docker images loaded into Minikube's internal Docker daemon (no external registry)

**Testing**:
- **Pre-deployment**: Helm chart linting (`helm lint`), Dockerfile validation (hadolint or Gordon)
- **Deployment**: Dry-run validation (`helm install --dry-run`)
- **Post-deployment**: Automated smoke tests (scripts/validate-deployment.sh) - pod status, health probes, CRUD operations, resource utilization

**Target Platform**:
- **Primary**: Minikube 1.32+ on Docker driver (local Kubernetes 1.28+)
- **Host OS**: Linux, macOS, Windows (Docker Desktop required)
- **Cluster Config**: 2+ CPUs, 4GB+ memory, 20GB+ disk

**Project Type**: Web application (Frontend + Backend + Database)

**Performance Goals**:
- **Deployment Time**: < 10 minutes from `minikube start` to frontend accessible (SC-001)
- **Pod Startup**: All pods "Running" within 2 minutes of Helm install (SC-002)
- **Frontend Access**: Accessible via browser within 30 seconds (SC-003)
- **Concurrent Users**: Support 2 concurrent users performing CRUD operations without degradation (SC-004)
- **Health Check Success Rate**: > 99% over continuous operation (SC-005)

**Constraints**:
- **Local Only**: Minikube deployment; no cloud providers (AWS, GCP, Azure)
- **AI-Generated Artifacts**: All Dockerfiles, Helm charts, manifests generated by AI agents (no manual coding per Constitution Principle I)
- **Image Size**: Frontend < 50MB, Backend < 100MB (multi-stage builds with Alpine)
- **Resource Limits**: Frontend (200m CPU, 256Mi memory), Backend (500m CPU, 512Mi memory), Database (500m CPU, 1Gi memory)
- **No Production Security**: TLS, network policies, pod security policies out of scope for Phase IV
- **Independent Services**: Frontend and Backend independently deployable (separate Helm charts, images, lifecycles)

**Scale/Scope**:
- **Replicas**: Frontend 2 (configurable), Backend 1 (configurable), Database 1 (single instance for Phase IV)
- **Services**: 3 Helm charts, 3 Docker images, 6+ Kubernetes resources per service
- **Documentation**: README.md, quickstart.md, data-model.md, research.md, contracts/

```
┌─────────────────────────────────────────────────────────────────┐
│                      Implementation Flow                         │
└─────────────────────────────────────────────────────────────────┘

Step 1: Dockerfile Generation
    Agent: Gordon (Docker AI Agent)
    Input: frontend/ and backend/ source code from Phase III
    Output: frontend/Dockerfile, backend/Dockerfile
    Validation: docker build succeeds, image size < targets
    Fallback: Claude generates Dockerfiles following Gordon patterns

Step 2: Docker Image Building
    Agent: Docker CLI (orchestrated by Claude)
    Input: Dockerfiles from Step 1
    Commands:
      - docker build -t todo-frontend:1.0.0 ./frontend
      - docker build -t todo-backend:1.0.0 ./backend
    Output: Docker images tagged and ready
    Validation: docker images list shows tags

Step 3: Load Images into Minikube
    Agent: Minikube CLI (orchestrated by Claude)
    Input: Docker images from Step 2
    Commands:
      - minikube image load todo-frontend:1.0.0
      - minikube image load todo-backend:1.0.0
    Output: Images available in Minikube's Docker daemon
    Validation: minikube image ls | grep todo-

Step 4: Helm Chart Generation
    Agent: Claude Sonnet 4.5
    Input: Helm chart specifications from contracts/
    Output: charts/frontend/, charts/backend/, charts/database/
    Components per chart:
      - Chart.yaml (metadata)
      - values.yaml (default configuration)
      - templates/ (deployment, service, configmap, secret, etc.)
      - _helpers.tpl (template functions)
      - NOTES.txt (post-install instructions)
      - README.md (chart documentation)
    Validation: helm lint passes, helm template renders valid YAML

Step 5: Helm Chart Deployment (Database)
    Agent: Helm CLI (orchestrated by Claude)
    Input: charts/database/
    Command: helm install todo-database charts/database
    Output: StatefulSet, Service, PVC created
    Validation:
      - kubectl wait --for=condition=ready pod/todo-database-0 --timeout=120s
      - kubectl get pvc (PVC bound)
      - mongosh connectivity test
    Fallback: Use kubectl-ai for troubleshooting if deployment fails

Step 6: Helm Chart Deployment (Backend)
    Agent: Helm CLI (orchestrated by Claude)
    Input: charts/backend/
    Dependency: Database must be running (Step 5)
    Command: helm install todo-backend charts/backend
    Output: Deployment, Service, ConfigMap, Secret created
    Validation:
      - kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=backend --timeout=120s
      - Health probe check: curl http://backend-service:5000/health
    Fallback: Use kubectl-ai for troubleshooting if deployment fails

Step 7: Helm Chart Deployment (Frontend)
    Agent: Helm CLI (orchestrated by Claude)
    Input: charts/frontend/
    Dependency: Backend must be running (Step 6)
    Command: helm install todo-frontend charts/frontend
    Output: Deployment (2 replicas), Service, ConfigMap created
    Validation:
      - kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=frontend --timeout=120s
      - Access via NodePort: minikube service todo-frontend-service --url
      - Frontend loads in browser
    Fallback: Use kubectl-ai for troubleshooting if deployment fails

Step 8: Cluster Health Analysis
    Agent: kagent (Kubernetes intelligence)
    Input: Deployed cluster state
    Commands:
      - kagent analyze cluster
      - kagent analyze deployment frontend
      - kagent analyze deployment backend
      - kagent analyze resources
      - kagent audit security
    Output: Health report, best-practice recommendations, resource optimization suggestions
    Validation: No critical issues flagged
    Fallback: Use kubectl top, kubectl get, kubectl describe if kagent unavailable

Step 9: End-to-End Smoke Tests
    Agent: Bash script (orchestrated by Claude)
    Input: scripts/validate-deployment.sh
    Tests:
      1. Cluster running (kubectl cluster-info)
      2. All pods ready (kubectl wait --for=condition=ready pod --all)
      3. Frontend accessible (curl frontend URL)
      4. Backend healthy (curl http://backend-service:5000/health)
      5. Database accessible (mongosh connection test)
      6. CRUD operations (POST/GET/PATCH/DELETE /todos)
      7. Resource utilization (kubectl top nodes, kubectl top pods)
    Output: Validation report (PASS/FAIL for each test)
    Validation: All tests pass (100% success rate per SC-006)
```
