## Core Principles

### I. AI-First Development (NON-NEGOTIABLE)

**No manual coding by humans.** All code, configuration files, Dockerfiles, Helm charts, and Kubernetes manifests MUST be generated by AI agents.

**Rationale**: Phase IV tests the capability of AI agents to handle full-stack infrastructure-as-code development without human intervention. This ensures reproducibility, consistency, and validates the Agentic Dev Stack approach.

**Enforcement**:
- All artifacts must be produced by agents (Gordon, kubectl-ai, kagent)
- Human role limited to: prompt engineering, validation, approval
- Any manual edits must be documented as exceptions with justification

---

### II. Cloud-Native Best Practices

**Follow cloud-native principles** as defined by CNCF (Cloud Native Computing Foundation). All deployments must be containerized, scalable, and follow 12-factor app methodology where applicable.

**Rationale**: Prepares codebase for production-grade cloud deployment and ensures maintainability, portability, and modern operational standards.

**Requirements**:
- Applications packaged as OCI-compliant containers
- Stateless services preferred; state externalized where possible
- Health checks (liveness, readiness) mandatory for all services
- Resource limits and requests defined for all deployments
- Secrets management via Kubernetes Secrets (not hardcoded)
- Environment-based configuration (ConfigMaps, env vars)

---

### III. Local-First Deployment

**Target platform is local Minikube only.** No cloud providers (AWS, GCP, Azure) in Phase IV scope.

**Rationale**: Reduces complexity, cost, and external dependencies. Focuses on core Kubernetes competency before adding cloud-specific abstractions.

**Constraints**:
- All testing and validation must run on local Minikube
- No cloud-specific resources (e.g., AWS Load Balancers, GCP PubSub)
- Use LoadBalancer service type with Minikube tunnel where needed
- Persistent volumes use local storage classes

---

### IV. Helm Over Raw Manifests

**Prefer Helm charts for all Kubernetes deployments.** Raw manifests allowed only for bootstrapping or one-off debugging.

**Rationale**: Helm provides templating, versioning, rollback capability, and reusable packaging—essential for maintainable infrastructure-as-code.

**Guidelines**:
- Each microservice gets its own Helm chart
- Use values.yaml for environment-specific overrides
- Chart version must follow semantic versioning
- Include README.md in each chart documenting parameters
- Validate charts with `helm lint` before deployment

---

### V. Independent Containerization

**Frontend and Backend must be independently containerized.** Each service has its own Dockerfile, image, and deployment lifecycle.

**Rationale**: Enables independent scaling, deployment, and versioning. Follows microservices best practices.

**Requirements**:
- Separate Dockerfiles for frontend and backend
- Each service builds to a distinct image (tagged with version)
- Services communicate via internal Kubernetes DNS
- No shared volumes between frontend and backend
- Each service has independent resource allocation

---

### VI. Build on Phase III

**Assumes Phase III Todo AI Chatbot is implemented and functional.** Phase IV focuses on containerization and orchestration, not application logic.

**Rationale**: Phase IV is about deployment, not feature development. Existing application code is the input.

**Acceptance**:
- Frontend and Backend code exist and run locally (Phase III deliverable)
- API contracts defined and stable
- Database schema established
- No new application features added in Phase IV

---

### VII. Reproducibility, Explainability, Evaluability

**System must be reproducible, explainable, and evaluatable (REE).**

**Reproducibility**: Any developer can clone the repo, run `minikube start` + `helm install`, and have the system running locally in under 10 minutes.

**Explainability**: All architecture decisions documented in ADRs. All infrastructure changes traceable via PHRs.

**Evaluability**: Health checks, readiness probes, and logs allow verification that deployment succeeded and system is operational.

**Deliverables**:
- `README.md` with step-by-step setup instructions
- `docs/deployment.md` with architecture overview
- All Dockerfiles and Helm charts with inline comments
- Smoke test script validating deployment (`scripts/validate-deployment.sh`)

- Document agent interactions in PHRs
- Validate agent outputs (linting, dry-run) before applying
- Log agent tool calls for traceability

## Deployment Architecture

### Target Environment

- **Platform**: Minikube (local Kubernetes cluster)
- **Kubernetes Version**: 1.28+ (latest Minikube default)
- **Container Runtime**: Docker (via Minikube's Docker driver)
- **Ingress**: Nginx Ingress Controller (Minikube addon)
- **Storage**: hostPath (local persistent volumes)

## Development Workflow

### Phase IV Workflow

1. **Setup**: Initialize Minikube, enable addons (ingress, metrics-server)
2. **Containerization**:
   - Generate Dockerfiles using Gordon
   - Build and tag images
   - Push to Minikube's local registry (or load directly)
3. **Helm Chart Creation**:
   - Generate chart templates for each service
   - Define values.yaml with sensible defaults
   - Include health checks and resource limits
4. **Deployment**:
   - Install charts: `helm install <release> <chart>`
   - Verify pods running: `kubectl get pods`
   - Check logs: `kubectl logs <pod>`
5. **Validation**:
   - Run smoke tests (API health endpoints)
   - Access frontend via Ingress URL
   - Verify end-to-end functionality (create/read/update/delete todos)
6. **Documentation**:
   - Create PHR for deployment session
   - Suggest ADR if architectural decisions made (e.g., database choice, ingress strategy)

### Constitution Checks (for `/sp.plan`)

Plans must validate against these gates before proceeding:

- [ ] **AI-Generated Artifacts**: Confirm all Dockerfiles, Helm charts, manifests will be agent-generated
- [ ] **Cloud-Native Compliance**: Services containerized, health checks defined, resource limits set
- [ ] **Local Minikube Target**: No cloud-specific resources referenced
- [ ] **Helm Preferred**: Deployment strategy uses Helm charts, not raw manifests (unless justified)
- [ ] **Independent Services**: Frontend and Backend have separate images and deployments
- [ ] **Phase III Foundation**: Application code exists and is functional (no new features in Phase IV)
- [ ] **REE Requirements**: README, deployment docs, smoke tests planned

## Non-Goals (Out of Scope)

The following are **explicitly excluded** from Phase IV:

- ❌ Cloud provider deployment (AWS, GCP, Azure)
- ❌ Production-grade security hardening (mTLS, pod security policies, network policies)
- ❌ CI/CD pipelines (GitHub Actions, Jenkins, GitLab CI)
- ❌ Monitoring/observability stacks (Prometheus, Grafana, ELK)
- ❌ Advanced autoscaling (HPA, VPA, cluster autoscaler)
- ❌ Multi-cluster or multi-region deployments
- ❌ Service mesh (Istio, Linkerd)
- ❌ GitOps workflows (ArgoCD, Flux)

**Rationale**: These are deferred to future phases to maintain focus on core Kubernetes and Agentic Dev Stack competency.

## Governance

### Constitution Authority

This constitution supersedes all other practices and guidelines for Phase IV. Any conflicts between this document and other documentation must be resolved in favor of this constitution.

### Amendment Process

1. **Proposal**: Amendments must be documented in a GitHub issue or discussion
2. **Review**: Proposed changes reviewed by project stakeholders
3. **Approval**: Requires explicit user consent
4. **Migration**: Update all dependent templates (spec, plan, tasks) and documentation
5. **Versioning**: Increment constitution version per semantic versioning rules

### Semantic Versioning for Constitution

- **MAJOR** (X.0.0): Backward-incompatible changes (e.g., removing a core principle, changing fundamental workflow)
- **MINOR** (x.Y.0): New principles added, sections expanded (backward-compatible)
- **PATCH** (x.y.Z): Clarifications, typo fixes, non-semantic refinements

### Compliance Verification

- All PRs must pass constitution checks before merge
- `/sp.plan` command validates against constitution gates
- PHRs must be created for all implementation sessions
- ADRs suggested for architecturally significant decisions (three-part test: Impact, Alternatives, Scope)

### Complexity Justification

Any violation of constitution principles (e.g., using raw manifests instead of Helm) must be justified in the plan.md Complexity Tracking section with:
- **Violation**: What principle was violated
- **Why Needed**: Specific problem requiring the exception
- **Simpler Alternative Rejected Because**: Why the constitutional approach was insufficient
